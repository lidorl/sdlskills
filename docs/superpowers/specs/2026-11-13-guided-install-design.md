# Guided install — design

Status: DRAFT (awaiting approval)

## Intent

First-time adopters can't tell what the kit expects. A recent adopter lacked the GitHub CLI and Copilot, never understood the *meta-root* concept, and installed the kit straight into their code repository. The installer printed too little for them to notice or recover. This work makes the first install self-explanatory, in the installers and in the README.

## Goals

- A first-time user understands, before anything is written, **what a meta-root is** and that it is not their code repository.
- Missing prerequisites are named, with how to fix each, before install.
- Installing into something that looks like a code repository is caught and questioned.
- The user sees what will be written and confirms.
- After install, a clear summary: what was done, what is still missing, next steps in order.
- The README explains the same things, so a user who reads it first gets the same picture.

## Non-goals

- Re-run validation / `--check` mode and superpowers detection. Parked in `docs/kit-open-items.md`; this design should not block it, and the prerequisite check is a natural seed for it.
- Fixing the Copilot thin-plan problem (same open item).
- Installing prerequisites for the user. The guide says what to install; it does not install Node, git or a CLI.
- A GUI, a non-Node implementation, or new dependencies.

## Anti-goals

- Breaking scripted use. Every existing invocation with a `<target-dir>` argument keeps working, with the same exit codes and file results.
- Hanging in CI or any non-interactive shell.

## Constraints

- Zero dependencies. The installer runs before `npm install` in the target, so it uses only Node built-ins (`node:readline/promises`).
- The kit is authored for Claude Code; Copilot output is generated by the `REWRITES` table in `install-sdlc-copilot.mjs`. Any new user-facing text in the installers or README must survive that rewrite, and `npm test` fails on Claude references that leak through it.
- `scripts/` is copied wholesale into adopters' projects (except `install-sdlc*`). New shared helpers go in `scripts/lib/`.

## Behavior

### When it is interactive

- **No `<target-dir>` argument and stdin and stdout are TTYs:** run the guided flow.
- **`<target-dir>` given:** today's non-interactive behavior, plus the new prerequisite notes and code-repo warning printed as warnings (never prompting, never blocking).
- **No argument and not a TTY:** print usage and exit 1, as today.
- No `--yes` flag: passing a `<target-dir>` already means non-interactive.

### The guided flow

1. **Explain.** Two or three sentences: the kit lives in a separate *meta-root* repo that holds the process, skills and the `docs/` trail; your code repositories stay untouched and are checked out under `workspace/` when work starts. A small folder diagram.
2. **Say which tool this installer is for.** `install-sdlc.mjs` is for Claude Code, `install-sdlc-copilot.mjs` for GitHub Copilot. The guide names the one the user ran and prints the command for the other, in case they picked wrong.
3. **Prerequisites.** Check and report each line as ok / missing / optional, with a fix:
   - Node 20 or newer (required).
   - git (required).
   - The tool's CLI: `claude` for Claude Code; `copilot` for Copilot. For Copilot this is optional, since VS Code agent mode works without the CLI, but the plugin install needs it.
   - GitHub CLI `gh` (optional now, needed at close-out for PR verification).
   Required items that are missing stop the flow with the fix. Optional ones continue.
4. **Ask where to install.** Default: a new folder next to the current directory, named after it plus `-workspace` (e.g. `acme-api` → `acme-api-workspace`). The user can type any path. If the path doesn't exist, offer to create it.
5. **Code-repo check.** If the chosen path looks like a code repository, warn and ask: continue, pick another path, or quit. "Looks like code" means it is a git repo with a source signal: a `src/`, `app/` or `lib/` directory, or a build manifest (`package.json` with `dependencies` beyond the kit's own, `pyproject.toml`, `go.mod`, `pom.xml`, `Cargo.toml`, `*.csproj`). A directory already holding the kit (`.claude/skills/` or `.github/skills/` with kit skills) is never flagged.
6. **Show the plan** — the same action list `--dry-run` produces — and ask to proceed.
7. **Install**, then print the summary.

### The summary (all modes)

After install, always print three blocks: **Done** (the action list), **Needs attention** (warnings: missing CLI, plugin not installed, `npm install` failed, not a git repo), **Next steps** (numbered, in order, each a single command or action, including "open this folder in your tool and run `/setup-sdlc`").

### README

Replace "Using it in a project" with:

- **Before you start:** the prerequisites table (required vs optional, why each).
- **What's a meta-root:** the concept and folder diagram, stated as "install here, not in your code repo."
- **Install:** one command for Claude Code, one for Copilot, noting that running with no arguments starts the guided flow.
- **What you'll see:** an abbreviated sample of the guided flow and summary.
- **After install:** the numbered next steps, matching the installer's.
- **Troubleshooting:** installed into a code repo by mistake (how to undo); a prerequisite is missing; Windows notes.

## Parts decided by the user

- Interactive guide as the default with no arguments; flags kept for scripting.
- Cover prerequisites, the meta-root concept, install steps, and clearer script output, plus README.

## My calls (please check)

- The tool is chosen by which script the user runs; the guide confirms it and points to the other script rather than asking and switching layouts. (Avoids a circular import between the two installers.)
- Node 20+ as the floor (the scripts use `readdirSync({ recursive })` and `node:test`); no `engines` field exists today.
- `gh` is optional at install time because only close-out uses it.
- Default install path is a sibling `<name>-workspace` folder (the user's choice; note the kit also creates a `workspace/` folder inside the meta-root for repo checkouts, so the README must keep the two distinct).
- The code-repo heuristic above, and that it only warns.
