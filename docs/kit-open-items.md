# Kit Open Items

Unresolved design questions about the SDLC kit itself (not about any project that adopts it). Each is a specific deferred decision from work already done. Larger, less-formed directions live in [`../BRAINSTORMING.md`](../BRAINSTORMING.md).

## Open Items

- [ ] **Per-worker signing for board writes.** The coordinator in [`feat-req/board-write-coordinator.md`](feat-req/board-write-coordinator.md) checks identity at the owner level: the PR author must be the worker's registered owner. All of one owner's workers share that GitHub login, so a buggy or confused worker could write under a sibling's id. Option: give each worker its own SSH signing key at `sdlc worker create`, record the public key in `board/workers/<id>.yml`, and have the coordinator verify commit signatures. The cost is key management (rotation, retire, a lost home directory). Decided for now: **owner-level identity**, with branch, `Worker:` trailer and PR title required to agree. (From the 2026-11-23 interview for that spec.)

- [ ] **Local coordinator for board writes.** The coordinator in [`feat-req/board-write-coordinator.md`](feat-req/board-write-coordinator.md) runs as a GitHub workflow, which costs Actions minutes for each run. A second way to run it is `sdlc coordinator` on an always-on machine: it polls open board PRs and merges or closes them with the same validation library, using no Actions minutes. The costs are always-on infrastructure the kit has avoided so far, and a single point of failure. Decided for now: **workflow only**, with `writes: direct` as the fallback for small adopters. (From the 2026-11-23 interview for that spec.)

- [ ] **Same-model review for single-model adopters.** The independent verification spec ([`feat-req/independent-verification.md`](feat-req/independent-verification.md)) requires the verify run to differ from the implement run in model or worker, so an adopter with one agent CLI and one model always reviews by hand at the gate. Option: allow a same-model, same-worker review only when policy opts in (`require_different: none`), record it as `independence: weak`, and flag it prominently at the human gate. Decided for now: **strict**, a same-model review never counts. (From the 2026-11-23 interview for that spec.)

- [ ] **Parallel agents / task claiming.** The current process (`select-next-task`, unified queue, `status: IN_PROGRESS`) assumes a single worker. Supporting 2+ agents needs: task claiming vs. locking, stale-claim recovery, worktree/branch isolation, merge/review ordering, and how `render-status.mjs` reflects concurrent work. Decided for now: **single worker**. (The broader multi-repo *execution environment* idea is [`BRAINSTORMING.md`](../BRAINSTORMING.md) §1 — related but a separate axis.)

- [ ] **`writing-plans` frontmatter contract.** `write-execution-plan` stamps `status`/`feat_req`/`design` onto the plan file *after* `superpowers:writing-plans` runs. If the upstream skill's output format changes, the stamp step may need updating. Watch for drift on `superpowers` upgrades.

- [ ] **Trivial-tier history entries and `render-status.mjs`.** Trivial changes produce a `docs/history/` entry but no feat-req, so they never appear in `docs/STATUS.md`. Fine for now (STATUS.md tracks features, not every commit), but if trivial-change volume matters, consider a rollup.

- [ ] **Workspace path drift for out-of-repo tooling.** `workspace/<key>/` is a normal checkout, so in-repo build / Docker / test scripts work unchanged. The gap is tooling that hard-codes a checkout path *outside* the repo — a CI runner config, an IDE workspace file, a sibling-repo relative import. Decided for now: document the `workspace/<key>/` convention and let adopters symlink a stable path if their tooling needs one. Revisit if it bites in practice. (From the 2026-09-09 external architectural review.)

- [ ] **Multi-repo partial-merge recovery.** The plan sets merge order and `close-out` verifies a merged PR per repo, but nothing defines the procedure when an early repo's PR merges and a later one then fails review or needs rework — the system sits briefly in a partial state. Options: require every PR approved before any merges; a documented rollback/hold procedure; feature-flag the cross-repo seam. Decided for now: merge order + "all PRs open and approved before the first merge" as guidance; formal atomicity deferred. (From the 2026-09-09 external architectural review. Related: execution-environment Open Questions.)

- [ ] **Re-run validation and superpowers visibility (Copilot first).** Two linked gaps. (1) Re-running the installer on an already-installed repo refreshes the vendored files but never reports what was missing or fixed, so someone who installed before the Copilot CLI existed can't tell whether their setup is complete. Idea: a status checklist on every re-run (skills, scripts, process/stack docs, hook file, `package.json`, superpowers), possibly a read-only `--check` mode. `copilot plugin list` exists on the Copilot CLI (v0.0.410), so superpowers can be detected there; VS Code can't be queried, so the report would say "can't tell". (2) A Copilot user got a quick, thin plan from `write-execution-plan` even though superpowers was (probably) installed. The Copilot rewrite turns `superpowers:writing-plans` into a bare `writing-plans`, and Copilot has no Skill tool to call it, so the agent may have written the plan itself instead of loading the real skill. Unconfirmed: check the transcript for "I'm using the writing-plans skill", or run the skill through the Copilot CLI and watch. Candidate fixes: say "from the superpowers plugin" in the rewrite; a hard stop in wrapping skills when the wrapped skill isn't loaded; the status report above. Decided for now: nothing built. Affects `write-execution-plan`, `write-design-doc`, `write-feature-request`, `close-out`.
