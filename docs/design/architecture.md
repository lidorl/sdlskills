# Architecture

The kit has no application code. Its "architecture" is the shape of the process and the artifacts it produces.

## Meta-root

An adopting project is a **meta-root** git repo:

```
<meta-root>/
├── CLAUDE.md                  → references CLAUDE.process.md + CLAUDE.stack.md
├── CLAUDE.process.md          the lifecycle contract (from the kit, unchanged)
├── CLAUDE.stack.md            the project's stack conventions (from setup-sdlc)
├── repos.yml                  repository catalog — which repo does what
├── repos/<key>.md             deeper per-repo notes (optional)
├── .claude/skills/            phase skills, symlinked from the kit
├── scripts/                   render-status · assemble-env · clean-env · lib/catalog
├── package.json               one dependency: yaml
├── docs/
│   ├── feat-req/  design/  plans/  history/  decisions/
│   └── STATUS.md              generated by render-status.mjs
└── workspace/                 git-ignored; per-effort code checkouts
    ├── .current-effort        marker: which effort is assembled
    └── <key>/                 a plain clone of the repo, own git history
```

The meta-root is version-controlled and shared. `workspace/` is not — each checkout is a plain clone that self-versions.

## Layers

```
skills (markdown, agent-executed)
  → read/write docs/ artifacts + repos.yml
  → shell out to scripts/ (render-status, assemble-env, clean-env)
      → git / gh / the yaml parser
```

- **Skills** own the process steps. They never contain project state.
- **`docs/` artifacts** are the state — feature-request `status` frontmatter is the single source of truth for lifecycle position.
- **`scripts/`** are pure, testable Node (`node:test`), zero-judgment: catalog parsing, workspace assembly, status rendering.

## Multi-repo

Multi-repo is the default; a solo project is N=1 (one catalog entry, one checkout). The effort's repo set is resolved during Design, locked at approval into the design doc's `repos:` frontmatter, and carried into the plan. `classify-change` runs per repo; `close-out` verifies a merged PR per repo. See `docs/decisions/001`–`004` and `docs/design/execution-environment.md`.

## Key invariants

- One feature request → one design doc → one (or more) plan(s), all filename-matched.
- `status` lives only in feature-request frontmatter. No filename prefixes.
- Section anchors in design docs and plans (`## Open Items`, `## Repositories`, `## Pull Requests`, `### Merge order`) are a format contract — skills and `render-status.mjs` parse them.
- Generated files (`docs/STATUS.md`, `docs/.status.json`) are never hand-edited.
