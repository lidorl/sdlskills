Step 2

Create your SDLC repo

The factory lives in its own repo — your SDLC repo, or meta-root — next to your code, never inside it. Clone this repo, then run the installer:

git clone https://github.com/lidorl/sdlskills.git
node sdlskills/install-sdlc.mjs

It asks which tool you use, then guides you: where to create the SDLC repo, whether it looks like a code repo by mistake, and one question that decides whether you get a factory:

? Will this project run workers, or share one board across several people?
  Yes
❯ No

Answer Yes to create the board now (board/ and board/config.yml). You can also add it later. It shows what it will do and asks before doing anything, then ends with Done, Needs attention and Next steps.

What you get:

acme-workspace/            your SDLC repo
├── CLAUDE.md              imports the two docs below (Claude Code)
├── CLAUDE.process.md      the process every station follows
├── CLAUDE.stack.md        your stack's conventions (adapt it)
├── .claude/skills/        the nine phase skills (.github/skills/ for Copilot)
├── scripts/               sdlc CLI, status, workspace checkout
├── docs/                  feature requests, designs, plans, history
├── board/                 the work board (if you said Yes)
└── workspace/             code checkouts, created per effort

For scripts and CI: node sdlskills/scripts/install-sdlc.mjs <dir> [--board] [--dry-run] (Claude Code) or install-sdlc-copilot.mjs (Copilot). Re-run it any time to update the skills and scripts; your edits to CLAUDE.md, the stack doc, package.json, .gitignore and board settings are kept.

Step 3

Set it up

  1. Install the superpowers plugin if the installer couldn't — it prints the exact command.

  2. Commit and push the SDLC repo to a remote your team (and your workers) can reach.

  3. Open the SDLC repo in Claude Code or Copilot and run /setup-sdlc. It maps your code repos into repos.yml, adapts CLAUDE.stack.md, and asks which steps should stop for you — the autonomy policy. Triage, design approval and review findings always stop.

Step 4

Your first effort, in one session

Run one effort by hand first. You're the operator: you start each station, and the agent follows the process.

  1. /write-feature-request — the agent interviews you, writes docs/feat-req/<name>.md, and asks you to accept, park or reject it.

  2. /select-next-task — ranks everything in flight and every accepted request, picks one and routes it. With the board on, it also claims it for you.

  3. /classify-change — trivial, standard or hotfix. A standard change continues below.

  4. /write-design-doc — the design, which you approve. Then /write-execution-plan.

  5. Development runs the plan test-first with the superpowers execution skills, then /code-review (and /security-review when it applies).

  6. /close-out walks the Definition of Done and marks the effort IMPLEMENTED.

Where things stand: docs/STATUS.md, regenerated after each session, or npm run status.

Step 5

Turn on the board

The board is your SDLC repo's main branch. Claims, progress and requests are small commits there; nothing else coordinates the work.

  • If you answered No at install, re-run the installer with --board — or just create your first worker, which adds board/ for you.
  • Every worker owner needs to push to main directly. Protect it against force-pushes, not against pushes.
  • Give push rights only to people you'd trust to run code on the worker machines: workers run the repo's own scripts, and their agent loads its CLAUDE.md and skills.
  • Log in to GitHub for git: gh auth login, then gh auth setup-git.

Settings live in board/config.yml, shared by everyone on the board:

lease_ttl: 4h            # a claim with no report for this long is stale; anyone may take it over
idle_poll: 60s           # how often an idle worker looks for work
phase_timeout: 3h        # the longest one agent run may take (must be shorter than lease_ttl)
backoff: [5m, 15m, 60m]  # waits after consecutive failures
watch_interval: 30s      # default refresh for sdlc watch
Step 6

Create a worker

A worker is a persistent process you own, with its own home (~/.sdlc/workers/<id>/) and its own clone of the SDLC repo. Create one per machine slot, from the SDLC repo's folder:

node scripts/sdlc.mjs worker create --agent claude --model claude-sonnet-5-5

It checks the agent CLI and model with one tiny prompt, clones the repo, installs its npm dependencies, and registers the worker on the board as <your-github-login>-<6 chars>. If anything fails, nothing is left behind.

  • The agent CLI must be a real binary on PATH. A shell alias isn't visible to the worker — put the binary in e.g. ~/.local/bin.
  • --agent copilot works the same way, but a Copilot worker runs shell commands without a sandbox: give it its own OS user or VM.
  • On a machine without a clone: npx -p github:<org>/<sdlc-repo> sdlc worker create ….
Step 7

Run workers

node scripts/sdlc.mjs worker start <id> --detach   # runs in the background; logs in ~/.sdlc/workers/<id>/logs/
node scripts/sdlc.mjs worker start <id>            # or in this terminal
node scripts/sdlc.mjs worker once <id>             # one phase of one effort, then stop
node scripts/sdlc.mjs worker stop <id>             # finishes cleanly: pushes code, reports, releases its claim
node scripts/sdlc.mjs worker list                  # your workers on this machine and their state

A running worker loops: claim the top effort it can take, apply any answers waiting for it, run one phase headless, report, and move on. It renews its claim while a long run is going. When it needs you, it posts a request and takes other work. Run as many as you like, on as many machines as you like — they never pick the same effort.

Your own sessions keep working too: /select-next-task claims through the same board, so a person and a worker never collide.

Step 8

Answer what workers ask

node scripts/sdlc.mjs inbox            # your open requests, oldest first (--all for everyone's)
node scripts/sdlc.mjs answer <id>      # shows the request and asks for your answer

Or answer in one line with --choice and --note:

RequestYour answers
Design approvalapprove · reject (with a --note saying what to change)
Triageaccept · park · reject
Review findingsone per finding: --choice F1=fix,F2=accept (give the rationale for any accept in --note)
Policy gateapprove · reject
Questionan option letter, e.g. --choice B · or text with your reply in --note
Clarificationconfirm · correct (with the correction in --note)
Error on an effortretry · park · text (instructions in --note)
Error on a workerresolved, once you've fixed it (e.g. logged gh back in)
 
node scripts/sdlc.mjs answer 202611230614-tzq2l3 --choice approve --note "Ship it."

Answering only writes the request file. The next worker to pick the effort up applies your answer — the design flips to approved, a fix becomes a plan step, a park parks it — and records the decision under the feature request's ## Decisions, citing the request.

Step 9

Watch the factory

node scripts/sdlc.mjs status     # workers by owner, efforts in flight with their claims, the inbox
node scripts/sdlc.mjs watch      # claims, reports, requests and answers as they land (--json for tools)
npm run status                   # regenerates docs/STATUS.md, with the same board view

These read the board on origin/main and never touch your checkout.

Step 10

Day two: change, recover, retire

  • Change a worker's model: sdlc worker config <id> --model <m> (while it's stopped).
  • A worker crashed: start it again. It notices, posts a worker error with the end of its log, and waits for you to answer resolved.
  • A machine died mid-effort: nothing to do. After lease_ttl another worker takes the effort over and resumes from the plan's first unchecked step.
  • Work you can't find: anything a worker had to set aside — leftovers from a lost or failed effort — is in ~/.sdlc/workers/<id>/salvage/, and the log says where.
  • Retire a worker: sdlc worker retire <id> releases its claim and deletes its home; its history stays on the board. It refuses while salvaged work exists unless you add --force.
Help

Troubleshooting

  • "agent CLI not found on PATH" — the CLI is a shell alias or not installed on that machine. Put the real binary on PATH.
  • "run gh auth login" — the claim or answer needs your GitHub login.
  • An effort error says "the agent changed … outside the effort's publishable docs" — the agent wrote somewhere a worker doesn't publish. The files are in salvage; finish that effort in an interactive session.
  • Installed into a code repository by mistake — git status shows what was added; delete it, restore package.json and .gitignore, and install into a new folder.
  • Windows — run the installer with node from PowerShell, cmd or Git Bash.
