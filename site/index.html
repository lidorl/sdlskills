The software factory

Specs in, merged PRs out. People decide at the gates.

A software factory turns a stream of feature requests into reviewed, merged changes with as little babysitting as possible. Agents do the work at each station; people step in only where a decision is theirs to make. The kit builds that out of parts you can see: a queue in git, workers you own, and requests that wait for you instead of blocking.

  • stations

    The lifecycle phases. Each one is a skill and leaves an artifact in a fixed place: spec, design, plan, history, close-out.

  • conveyor

    The work board: efforts are queued, claimed and tracked as small commits on main. No server.

  • operators

    Workers: persistent processes you own. Each claims the next effort, runs one phase headless, reports, and moves on.

  • gates

    Triage, design approval, review findings, and anything your autonomy policy holds back. A worker posts a request and takes other work instead of waiting.

  • inspection

    Reviews at each step and the Definition of Done. Nothing closes until every item holds.

  • shift log

    The docs/ trail and STATUS.md: what was decided, why, and where every effort stands.

You don't need the factory to use the kit — one interactive session follows the same process, and you're the operator. Not built yet: an independent verification stage, a coordinator that serializes board writes, and breaking large features into efforts.

Scaling out

Workers take the next effort. You answer what they ask.

A worker is a persistent process with its own home and its own clone of your SDLC repo, so several can run side by side on one machine or many. It claims an effort with a commit on main — the claim counts only once it lands — renews it with every report, and gives it up if it goes stale. When it needs a person it posts a gate, question, clarification or error to board/requests/ and moves on. Your interactive sessions claim through the same board, so you and the workers never pick the same effort.

# once per machine: register a worker on the board
node scripts/sdlc.mjs worker create --agent claude --model <model>
node scripts/sdlc.mjs worker start <id> --detach

# what's waiting on you, and your answer
node scripts/sdlc.mjs inbox
node scripts/sdlc.mjs answer <id>

# the board at a glance
node scripts/sdlc.mjs status
node scripts/sdlc.mjs watch

Turn the board on with --board at install (or answer Yes to the workers question). Workers push to main directly and run your repo's own scripts, so give push rights only to people you'd trust on the worker machines. Claude Code workers are tested end to end; Copilot workers aren't yet.

Why the process

A factory is only as good as its operating manual.

Agents left to their own judgment drift, and unattended agents drift further. So the factory runs on one opinionated process, and every skill and every worker exists to serve it. A change — whether it's a typo or a payments rewrite — moves through the same phases, produces the same artifacts in the same folders, and isn't done until a written Definition of Done says so.

Uniform ceremony on a trivial fix is how teams learn to route around process. So every change is first sorted into a tier, and the paperwork scales with the risk. And the gates that matter — a design you approve, a spec you accept, review findings you rule on — always stop for a human. The rest is yours to configure.

The process inside

One operating manual for every station

  • six phases

    Spec, design, plan, build, review, close-out. Each is a skill and leaves a document in a fixed place.

  • three tiers

    Trivial, standard or hotfix, decided before any code. The paperwork scales with the risk.

  • gates you set once

    An autonomy policy decides what stops for you. Triage, design approval and review findings always do.

  • multi-repo

    One SDLC repo holds the process and the trail; code repos are checked out only while an effort needs them.

  • definition of done

    Walked item by item before anything is marked finished — down to a merged PR in every repo.

  • one status field

    Every effort's position is one line in its feature request, and STATUS.md is generated from it.

Get started

Run one effort by hand, then hand it to workers

  1. Install into a new SDLC repo next to your code, and answer Yes to the workers question.

    node sdlskills/install-sdlc.mjs

  2. Run /setup-sdlc in Claude Code or Copilot, then take one effort through by hand: /write-feature-request, /select-next-task.

  3. Create and start a worker, and answer what it asks from your inbox.

    node scripts/sdlc.mjs worker create --agent claude --model <model>
node scripts/sdlc.mjs worker start <id> --detach
node scripts/sdlc.mjs inbox
