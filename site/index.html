Why it exists

The process is the point. The skills are just tooling.

Most skill collections are a grab-bag of capabilities. This one inverts that: every skill exists to serve one opinionated process. A change — whether it's a typo or a payments rewrite — moves through the same phases, produces the same artifacts in the same folders, and isn't done until a written Definition of Done says so.

Uniform ceremony on a trivial fix is how teams learn to route around process. So every change is first sorted into a tier, and the paperwork scales with the risk. And because an agent left to its own judgment drifts, the gates that matter — a design you approve, a spec you accept, review findings you rule on — always stop for a human. The rest is yours to configure.

Multi-repo by default

Your project is a meta-root, not a repo

Real work spans repositories — a feature touches the API, the web app, a shared library. So the kit doesn't sit in a repo. Your project is a meta-root: the process contract, the skills, the docs/ trail, and a repos.yml catalog that says which repo does what. Design resolves which repos an effort needs; assemble-env checks out just those under workspace/.

The repo set is locked at design approval. classify-change runs per repo; close-out won't mark a feature done until every repo has a merged PR. A solo project is just N=1 — one catalog entry, one checkout, same machinery.

The lifecycle

Six phases, each with a skill and an artifact

§1 · hard stopFeature Request

A product interview turns a raw ask into a spec — personas, scenarios, scope boundaries, acceptance criteria, success metrics — then a triage decision: accept, park, or reject.

  • skill/write-feature-request
  • artifactdocs/feat-req/<name>.md
  • setsstatus: ACCEPTED
§2 · hard stopDesign

A fixed-structure design doc: proposed design, data-model and API changes, alternatives considered, testing strategy, rollout. A technical brainstorm runs first when the solution space is non-obvious. Approval is non-negotiable.

  • skill/write-design-doc
  • artifactdocs/design/<name>.md
  • setsstatus: DESIGNED
§3Plan

Wraps superpowers:writing-plans to turn the approved design into an ordered, executable sequence — then pins its location, stamps its frontmatter, and links it back to the spec.

  • skill/write-execution-plan
  • artifactdocs/plans/<name>.md
  • setsstatus: PLANNED
§4Development

The plan is executed test-first. Between-phase checkpoints pause for your review or run straight through, per your autonomy policy. Testing isn't a separate phase — it's how the code gets written.

  • skillsuperpowers:executing-plans
  • skilltest-driven-development
  • setsstatus: IN_PROGRESS
§5 · hard stopCode / Security Review

Runs /code-review, and /security-review when auth, an external endpoint, data access, or API keys are touched. Findings are processed with rigor — verified before implemented, or rejected with a recorded reason.

  • skill/code-review
  • skill/security-review
  • skillreceiving-code-review
§6Close-out

Walks the Definition of Done item by item, updates consumer-facing docs, writes the history entry, reconciles the design doc's open items, and flips the feature to implemented.

  • skill/close-out
  • artifactdocs/history/<ts>_*.md
  • setsstatus: IMPLEMENTED
Proportional process

Three tiers. The paperwork scales with the risk.

/classify-change sorts every change before a line is written. Auth, data access, API surface, schema, and dependency changes are never trivial, whatever their size.

Trivial

A typo, a comment, a tightened type, a test-only change. No behavior, schema, API, auth, or dependency change; two files or fewer.

history one-liner + passing tests

Standard

Any feature or behavior change. The full lifecycle applies, end to end.

design → plan → build (TDD) → review → close-out

Hotfix

A shipped change is breaking production right now. A fast lane — with a debt marker attached.

minimal fix + tests + incident note + mandatory follow-up feature request
One source of truth

State lives in one field

ACCEPTED→ DESIGNED→ PLANNED→ IN_PROGRESS→ IMPLEMENTED

Plus PARKED and REJECTED off to the side. It's one key in the feature request's frontmatter — no duplicate state, no filename prefixes to keep in sync. A small script, render-status.mjs, derives docs/STATUS.md from it on every stop, so the dashboard can never disagree with reality.

You set the gates

An autonomy policy, decided once

A setup interview asks how much you want to be in the loop, with concrete examples. The answers become a block in your CLAUDE.md that every skill reads — hand-editable any time.

autonomy:
  task_selection:             confirm    # confirm | auto
  product_brainstorm:         discuss    # discuss | solo
  technical_brainstorm:       solo       # discuss | solo
  implementation_checkpoints: pause      # pause | run-through

Design-doc approval, feature-request triage, and review findings stop for you no matter what these say.

The tooling

Nine skills implement the phases

  • /setup-sdlc

    One-time adoption — maps the repo, writes the stack-conventions doc, runs the autonomy interview, optionally scaffolds docs/design/.

  • /write-feature-request

    Product interview into a spec, ending with a triage decision.

  • /classify-change

    Sorts the change — trivial, standard, or hotfix — before any code.

  • /write-design-doc

    Fixed-structure design doc, optional technical brainstorm, hard-stop approval.

  • /write-execution-plan

    Wraps writing-plans; enforces location, frontmatter, and state.

  • /write-history-entry

    The intent-vs-reality trace: deviations, discoveries, decisions, verification.

  • /select-next-task

    One ranked queue across every in-flight item; routes the pick to its phase.

  • /gather-open-items

    Reconciles deferred open items — resolves them or promotes them to feature requests.

  • /close-out

    Walks the Definition of Done, updates consumer docs, flips status to implemented.

Definition of done

A standard change isn't done until

  • a design doc describes the change
  • the execution plan has every step checked
  • architecture.md / data-model.md updated if structure or schema moved
  • README and consumer-facing docs updated — or "no impact" recorded
  • tests written test-first for new behavior
  • the full suite is green, with recorded evidence
  • /code-review run, findings addressed or ruled on
  • /security-review run when it's security-relevant
  • a history entry records deviations, discoveries, decisions
  • the design doc's open items are triaged
  • status: IMPLEMENTED
Get started

Layer it onto any repo

The kit ships no application code — it's a process contract plus skills, meant to sit on top of whatever you're building.

  1. Install the superpowers plugin — it provides writing-plans, brainstorming, and the execution and review skills.

    /plugin marketplace add claude-plugins-official
/plugin install superpowers@claude-plugins-official

  2. Copy CLAUDE.process.md into your repo and reference it from CLAUDE.md. Start your stack doc from CLAUDE.stack.example.md.

  3. Symlink the skills and the status script into your project.

    mkdir -p .claude/skills scripts
for s in setup-sdlc write-feature-request classify-change write-design-doc \
         write-execution-plan write-history-entry select-next-task \
         gather-open-items close-out; do
  ln -s /path/to/sdlskills/skills/$s .claude/skills/$s
done
cp /path/to/sdlskills/scripts/render-status.mjs scripts/

  4. Run /setup-sdlc and answer the interview. Then start the loop with /write-feature-request, and /select-next-task from there on.
